# Out of Scope

Everything below was deliberately excluded, most of it because it's exactly what made the three rejected alternatives ([[alternatives-evaluated]]) the wrong size for this problem.

- **Semantic/embedding-based search.** Recall is exact/keyword or simple recency-based, not vector similarity. No embedding model, no API key, no `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` dependency for the core mechanism to function.
- **Any persistent daemon or server process.** No port, no background worker, no engine to keep alive or restart. This directly rules out re-adopting `agentmemory`'s `iii-engine` architecture.
- **Multi-tenant, auth, or audit-log features.** There is one user on one machine. No API keys, no roles, no audit trail.
- **A goal-stack, policy-versioning, customer-notes, or project-brief subsystem.** These are `hippo-memory` features aimed at a much broader "second brain" product. x-memory is a handoff tool, not that.
- **A web dashboard.** Inspection happens via a CLI command (see [[user-stories#21|story 21]]), not a browser UI.
- **Support for more than two tools at launch.** Claude Code and opencode only. Extending to a third tool (Cursor, Codex, etc.) is a plausible future direction but not part of this spec, and shouldn't shape today's design beyond not actively foreclosing it.
- **Multi-machine sync.** The store is local to the machine it runs on. No cloud account, no cross-device sync — this is the exact requirement that disqualified `supermemory`'s handoff feature, which required a cloud API key even in "local mode."
- **Merging concurrent sessions' recaps into one coherent narrative.** Per [[docs/adr/0001-pull-based-indexing-over-push-based-capture]], there's no longer a shared write target to merge in the first place — each tool indexes from its own separately-stored sessions, and "current" is just whichever has the newer timestamp. Synthesizing a single narrative out of two concurrent sessions' work is a plausible future feature, not something this spec builds.
- **Hand-parsing either tool's internal session-storage format.** Both Claude Code's JSONL and opencode's internal SQLite database are explicitly out of bounds — see [[implementation-decisions#reading-through-stable-interfaces-hard-constraint|reading through stable interfaces]]. Only each tool's own documented, stable read surface is used.
- **A working-memory scratch buffer separate from the durable store.** Checked directly in `hippo-memory`'s source and live-tested: its `wm flush` is a plain delete with no promotion path into durable storage, so there is nothing to borrow — x-memory's incremental observation flush (see [[implementation-decisions#crash-resilience|crash resilience]]) already promotes in-session facts directly. See [[lessons-from-alternatives#rejected-checked-and-explicitly-not-worth-it|lessons from alternatives]].
- **An entity/relation knowledge graph.** Confirmed real and cheap in agentmemory (a deterministic cross-product over already-tagged concepts/files, no LLM required), but it answers "how do these memories relate to each other," not "what's the current recap for this project" — a different question than the one x-memory exists to answer.
- **Multi-agent task orchestration** — dependency-gated task graphs, distributed locks/leases, condition watchers. Confirmed real and fully implemented in agentmemory, but built for concurrent agents contending over a shared task graph. x-memory has one user on one machine and no lock contention to arbitrate.
- **A scheduled background consolidation job.** Already excluded by the no-daemon rule above; confirmed hippo-memory runs this via cron plus a `SessionEnd` hook, which would reintroduce exactly the always-running-process shape this spec rules out.
